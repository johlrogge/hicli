CLI-enable your code.

Write ordinary, well-typed, well-documented Rust functions. Get a command-line interface for them (help, completion, exit codes, tests) without writing a CLI.

hicli is a subcommand framework for Rust, built on bpaf. It doesn’t stand between your program and the command line: a command is a function with a doc comment, a group of commands is a module, and the functions stay plain Rust that you can call and test directly.

Chapter 1

Your program, CLI-enabled

A command-line tool is code first and interface second. Most CLI frameworks invert that: you describe the interface in their vocabulary, as a derive enum, a builder or a central dispatch match, and hang your code off it. Then you translate the parsed struct back into calls to the code you actually wanted to run.

A parser between you and your program

  • An enum Commands that every new command has to edit.
  • A match that dispatches it, growing with every command.
  • Each command’s name and help text written down twice.

hicli: your program, CLI-enabled

  • #[command] leaves the function exactly as written and adds a handle.
  • A #[group] module’s commands are discovered in source order. No list to keep in sync.
  • The doc comment is the help text, so it can’t go stale.

Example 1.1

Worked example: a group of commands

Three functions in a module. The doc comments become the help.

  1. The name comes from the function name, with _ turned into -: set_output becomes set-output.
  2. The first paragraph of the doc comment is the help. A command or group without one is a compile error.
  3. The function itself is unchanged: playback::stop(&ctx) still works.

1.2 Exercise

Wire up a command line for the three functions above. Write the dispatcher, the help text and the argument struct.

Answer (no peeking)

You already did. It’s your functions. There is no dispatcher to write and no help text to repeat: list the group in app! and you’re done.

Chapter 2

One function, one command

Everything about a command is in one place, in the language you already write, checked by the compiler you already run.

  • fna command
  • moda group
  • typean argument

2.1 A command is a documented function

Put #[command] on a function and it becomes a subcommand. Its first doc line is the summary, the following paragraphs are the description, and an # Examples section is printed at the end of its --help.

Use #[command(alias = "ls")] for another name and #[command(hide)] to keep a command out of help and completion.

2.2 A group is a module, inline or in its own file

#[group] on a module makes it a group. Its commands are the #[command] functions and #[group] modules inside it, in source order. Groups nest, so one module can hold another.

A big group can live in its own file: #[group] pub mod x; (MSRV 1.99, which made attribute macros on file-module declarations stable).

no list to keep in sync ✎

2.3 An argument is a type

set_output takes an Output, a newtype that derives Arg. #[arg(positional = "NAME")] says where it goes, and its doc comment is its help. Define it once and use it in every command that needs it.

A FromStr says what a valid value is: the newtype’s own if it has one, else the one of the type inside. Bad values never reach a command: a value that doesn’t parse is a usage error that names the argument, and no command runs. Chapter 3 has more on what a type can say.

2.4 The tree is composed, not dispatched

app! lists the top-level commands and groups by name. You don’t write a central enum Commands or a match that dispatches it. The context is built once from the globals, by the closure you pass to run, and handed to every command that takes &Ctx.

Exit codes: 0 on success, 1 for a runtime failure, 2 for a usage error. run returns the ExitCode; it never calls process::exit.

2.5 Object, then verb, and a default command

playr source bandcamp check-updates puts a value between the group and the command. Use #[group(args = T)] for the group and #[command(curried)] for each command that receives the value as its first parameter.

When a group has a #[command(default)], that command runs if no other command in the group is named: playr library archive lists the archive, playr library archive empty empties it.

2.6 ? on the errors you already have

A command can return whatever it already returns: (), Outcome, io::Result<()>, anyhow::Result<()>, color_eyre::Result<()>, Result<(), Box<dyn Error>>. Any error becomes a runtime failure (exit 1), and the message is the whole error chain, outermost first.

hicli never inspects an error to choose an exit code. It is a usage error (exit 2) only when it says so, with Failure::usage(..).

2.7 Completion lives on the type

Completion is attached to the argument type, so every command that takes a SourceName completes source names, and a Choice enum completes its names with no completer at all. For paths, use #[arg(complete = files)] or #[arg(complete = dirs)]. Command names complete automatically.

Chapter 3

Types that document themselves

Write what an argument is once, on its type. Its help, its allowed values, its completion and its error messages follow it into every command that takes it. A command can still say something more specific. The examples below are from the test suite, so the output is exactly what hicli prints.

3.1 The type’s doc comment is its help

The first paragraph of the doc comment on an argument type is its help row, in every command that takes it. SortOpt is spelled with #[arg(…)]: an option --sort (or -s) whose value is a Choice. Two commands take it and neither repeats a word of it.

The doc comment is required, so there is no argument without help. Anything after its first blank line is for rustdoc and is never printed.

3.2 The command adds the context

The type’s doc is the default. A command that can say something more specific lists the parameter in an # Arguments section of its own doc comment, named after the parameter. That replaces the help row for this command only.

Only the row changes. Usage, completion and errors stay the type’s, and the section is read, not printed. There are no parameter attributes: this is the one place a command talks about its arguments. Naming a parameter that doesn’t exist is a compile error.

3.3 A choice is a type that lists its names

A fieldless enum with #[derive(Choice)] is a fixed set of words. Add Arg and #[arg(positional = "KEY")] and the enum itself is the argument. It parses, completes and names itself in errors, with no completer to write. Its help row ends with the names, so don’t list them in the doc comment.

Each variant’s doc comment is the description a shell shows beside it when completing. A wrong word lists the names and, if one is close, suggests it.

3.4 Validated newtypes, with errors that name the argument

A spelled type is parsed by its own FromStr first, and only then by the type inside it. So a newtype over NonZeroUsize or PathBuf can carry its own rule, and every command that takes it gets the rule for free. A struct with several fields works too, when it is one word that its FromStr takes apart.

Say what is wrong with the word, as a phrase that reads after the argument’s name. hicli adds the word and the argument, spelled the way the user typed it (--limit, even for -l 0).

3.5 Exercise

You want --sort to say “Order for this listing” in one command and the type’s default everywhere else. How many attributes go on the parameter?

Answer

None. There are no parameter attributes: one # Arguments line in that command’s doc comment.

Chapter 4

Opinionated, on purpose

Programmer ergonomics over every possible command line. Always.

Where CLI expressiveness and a natural programming experience conflict, the programming experience wins. If a parsing feature would cost the function its ordinary shape, we leave the feature out.

from hicli’s VISION.md

You get a CLI with a hicli flavour: it follows hicli’s guidelines, so the same rules hold in every hicli program. The flip side is that not every command line can be expressed. If you need to reproduce some existing Unix tool’s interface flag for flag, quirk for quirk, reach for clap. hicli is for people who want their CLI to be a thin, typed, documented skin over code they would write anyway. So it says no to some things, and says so up front. Here are the rules of this book:

  1. Every argument is a newtype.

    There are no Arg impls for String, u64 and so on. A primitive in a command’s signature is a compile error, so the type carries its spelling, help, validation and completion once, for every command.

  2. No doc comment, no command.

    A command or group without a doc comment is a compile error. Help can’t be forgotten.

  3. Positionals go last in the signature.

    Parameters are parsed in the order they are declared, and bpaf requires the types that contain positionals to come last. On the command line, flags can still go anywhere.

  4. -7 is a flag, unless you glue it.

    Write --added=-7. hicli keeps to the standard rule rather than special-casing hyphen values: a parser that sometimes takes -7 as a value and sometimes as a flag surprises users.

  5. Globals are parsed once.

    They are accepted before or after the subcommand, but can’t be overridden per subcommand.

  6. The help looks like bpaf’s, not clap’s.

    A one-value argument is spelled with #[arg(…)] on its type, and anything bigger with bpaf’s own attributes. --help exits 0 and usage errors exit 2.

  7. One default command per group.

    None at the top level, and none in a curried group.

  8. Completers filter their own candidates.

    bpaf passes your completer’s results to the shell unchanged. It is handed the word as typed so far, so filter by it.

every rule here buys you a plain function.

Chapter 5

Testing without a terminal

The parser has no side effects, so the whole CLI can be tested in-process. You don’t need a subprocess or golden files.

  • cli! { … } turns the words you would type into an argv, and cli_test! writes one #[test] per line.
  • App::parse returns the parsed globals and the selected command, or the error that would be printed.
  • App::run_with_args runs everything and returns the exit code that main would.
  • App::complete returns what the shell would offer.
  • Commands are ordinary functions, so you can call them directly.

5.1 Exercise

How many processes does the test module above spawn?

Answer

None. Parsing, running and completion are all driven in-process, with the words you would type.
